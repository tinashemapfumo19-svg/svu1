## How it was made live

1. **Repository.** The rebuild was committed and pushed to GitHub `tinashemapfumo19-svg/svu1`. `_legacy_php_system/` (contains hard-coded legacy database credentials) and generated `data/*` output are git-ignored and were never pushed. `core.autocrlf=false` is set locally so files stay LF.
2. **Production readiness check (locally).** On a throwaway database with `SVU_ENV=production` and a fresh `SVU_DATA_KEY`: all migrations applied, `scripts/bootstrap-admin.js` created an admin and refused a second run, the server started, and the admin's sign-in returned `mfa_enrolment_required`. The scratch database was dropped.
3. **DNS.** In Namecheap Advanced DNS, A records `@` and `portal` were pointed at the droplet. A stray `@` record to `68.65.121.218` (Namecheap parking) was removed.
4. **SSH access.** Key `svu_droplet` was generated on the deploying PC and appended to `/root/.ssh/authorized_keys` through the DigitalOcean web console.
5. **Server setup.** `deploy/setup-droplet.sh portal.luminarytech.org` was copied to the droplet and run as root. It installs Node 22, PostgreSQL 16 and Caddy. It also adds 2 GB swap and creates the `svu` user, the database role and database (random password), `/etc/svu/svu.env` (random `SVU_DATA_KEY`, `SVU_MFA_POLICY=privileged`), the systemd unit, the Caddyfile, the nightly backup cron job and the firewall. It is idempotent and keeps existing secrets on re-run.
6. **Code deploy.** `deploy/deploy.sh root@157.230.89.193` was run from the PC. It streams `git archive HEAD`, so only committed code is deployed, into `/opt/svu/app.next`. It then runs `npm ci --omit=dev` and `node scripts/migrate.js` (migrations 001–118), swaps the directories, restarts `svu` and waits for `/api/health`. Revision `eeca607` went live.
7. **First administrator.** `scripts/bootstrap-admin.js` was run on the droplet with the production environment. It created the only account, `tinashemapfumo19@gmail.com` (System Administrator, MFA required), and printed a one-time temporary password to the owner. Every other account must be **invited from the app**. The script refuses to run once an administrator exists.
8. **Verified** from outside: `https://portal.luminarytech.org/api/health` reports `env: production` and database `ok`, the certificate is valid and HTTP returns 308 to HTTPS.

## Routine operations

All commands below run from Git Bash in the repo root on the owner's PC unless marked *droplet*.

```bash
# Deploy the committed HEAD (uncommitted changes are not shipped)
SVU_SSH_OPTS="-i $HOME/.ssh/svu_droplet -o IdentitiesOnly=yes" bash deploy/deploy.sh root@157.230.89.193

# Open a shell on the droplet
ssh -i ~/.ssh/svu_droplet root@157.230.89.193
```

On the droplet:

```bash
systemctl status svu                 # service state
journalctl -u svu -f                 # live app log
cat /opt/svu/app/REVISION            # deployed git revision
curl -s 127.0.0.1:4173/api/health    # local health check

# Roll back to the previous release (only if no new migration needs reverting)
systemctl stop svu && mv /opt/svu/app /opt/svu/app.failed && mv /opt/svu/app.previous /opt/svu/app && systemctl start svu

# Manual backup / restore
sudo -u postgres pg_dump -Fc svu_rebuild > /var/backups/svu/manual-$(date +%F-%H%M).dump
sudo -u postgres pg_restore --clean --if-exists -d svu_rebuild /var/backups/svu/<file>.dump
```

Migrations are forward-only. A rollback restores the previous code but not the schema, so restore a backup if a migration must be undone.

## Rules for agents (Codex and Claude)

- **Never run demo seeders** (`npm run seed`, `seed:json`, `demo:*`, `provision-role-logins.js`) against production. They are guarded to development and loopback databases, but do not try to work around that.
- **Only committed code deploys.** Commit, have the owner push, then run `deploy/deploy.sh`. Note the deploy in `docs/CODEX_CLAUDE_WORKSPACE.md`.
- **New migrations run automatically on deploy.** Test them against a fresh production-mode database first (step 2 above), not only the seeded development database.
- **Do not commit secrets.** Reference `/etc/svu/svu.env` variable names only.
- One deploy at a time. `deploy.sh` replaces `/opt/svu/app.next` and `/opt/svu/app.previous`.

## Known gaps in production

- **Document uploads are off.** Local storage is development-only until storage and malware scanning are decided (D-05, ADR-004).
- **Rate limits cannot tell visitors apart.** Behind Caddy, every request comes from 127.0.0.1, so per-IP limits (e.g. Ask SVU guidance) act as one shared bucket. Fix: trust `X-Forwarded-For` from the local proxy only.
- **Email, SMS, payments, push and AI are disabled** until their providers are configured.
- **The 38 `role.*` test logins in `docs/ROLE_LOGINS.md` exist only in local development**, not in production.
- **Backups are on the same droplet.** Enable DigitalOcean droplet backups or copy dumps off-site.
- Production bootstrap, identity and key custody still need formal sign-off (D-04/D-10, hosting model D-03).
