# Room Invitation Recipient Authority

## Contract

New invitations require a different active account, enabled room consent and at least one current, unended assignment through an active role granting `rooms.self`. Self authority may be scoped; it does not require institution-wide stewardship. Existing bilateral contact-block exclusions remain. Sender authority, current participation/moderation, room lifecycle, actor capacity and explicit recipient acceptance remain independent requirements.

The recipient query now joins and shared-locks account, preference, every qualifying assignment, active role and permission rows in deterministic grant order. It does not select an arbitrary single grant. A withdrawal whose row lock is acquired first must be observed after the invitation query waits; a valid invitation lookup whose shared locks are acquired first holds those selected rows through insertion/history/audit/receipt and transaction commit. This is a transaction boundary, not automatic cancellation of a retained pending invitation, response retraction, presence tracking, or proof against every unselected/new-row/clock boundary.

Existing actor-bound successful receipt replay remains before new recipient eligibility work, after fresh sender/room/moderator gates. An identical authorized retry returns the retained result without creating a new invitation; changed input conflicts. A fresh request must satisfy current recipient eligibility. Pending invitations do not imply participation or disclosure: acceptance uses the recipient's fresh authenticated authority and consent.

Messages remain as written after existing validation, without an automatic word filter. Rooms use account names without presence. No new institutional policy, nickname, online list, forced joining, working grant/consent or archive behavior is introduced.
