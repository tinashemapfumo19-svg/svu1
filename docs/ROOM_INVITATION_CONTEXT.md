# Room Invitation Command Context

Backend prerequisite in progress, 2026-10-12. This is not invitation recall UI, native database/router verification, working-server adoption or complete legacy command coverage.

## Contract

`POST /api/message-rooms/:id/invitation-command-context` reads metadata only. The mailbox is in the bounded JSON body `{email}`, never in a URL query. All query fields and unknown body fields are refused. The route sets `Cache-Control: no-store` before authentication, requires `rooms.self` and accepts only POST; the method is used for private lookup input, not a persisted command. No request key, old epoch, revision or recipient identity is accepted as authority.

The module reuses current room/self/moderator gates, including accepted actor participation/current consent and fresh global stewardship when a creator is not an assigned moderator. It takes a repeatable-read transaction, room advisory lock and the native private-contact pair lock. Canonical mailbox resolution must produce exactly one nonself account; after pair locking, eligibility is rechecked against the exact account/mailbox, active account and current eligible room-self grants, enabled preference and both block directions. Existing native invitation commands are unchanged and remain the final authority/quota gate.

The current consent-history row, latest retained room/recipient membership, actor membership/preference, room version, eligible recipient grant versions and retained inactive blocks bind the snapshot. A latest pending, accepted or banned membership is unavailable; declined/left/removed membership history participates in the epoch so a missed invitation lifecycle cannot revive stale context. The existing fifty-per-day invitation threshold is observed without writing or reserving capacity. It is not a guarantee of a future command's success.

The result contains only `{accountId,authorityEpoch,epoch,targetType:'invitation',targetId,operations:['invite']}`. `accountId` is the actor's own account. `targetId` is a keyed opaque room/recipient/canonical-mailbox identifier, not a raw peer ID. A separate domain-separated opaque epoch binds authority and recipient lifetimes. No peer mailbox/name/ID, grants, version rows, status, message body, reason or consent flag is returned. There is no command revision because the native invitation command does not accept one.

Malformed or inconsistent versions, consent, grant rows, membership shape, block rows or quota counts fail closed. Unknown, ambiguous, self, unavailable, blocked and already-participating recipients share the generic unavailable-contact refusal. Missing consent-history consistency is a reconciliation failure, not a silent repair. Serialization/deadlock failures become 409. The endpoint executes no domain/audit/notification/receipt insert, update, delete, acknowledgement, encryption, provider call or import.
