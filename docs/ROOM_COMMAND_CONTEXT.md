# Room Command Target Context

Verified backend prerequisite, 2026-10-12. Native target-specific recall controls are not implemented by this endpoint.

## Contract

Authenticated no-store `GET /api/message-rooms/:roomId/command-context?targetType=member|message&targetId=:id` accepts only those two query fields. Repeated/unknown fields and unsupported types are refused; authenticated non-GET requests return 405. It returns only `{accountId,authorityEpoch,epoch,targetType,targetId,revision,operations}`. Both epochs are opaque HMAC metadata, not grants or replay credentials, and no old epoch is accepted as input. Account ID belongs to the current caller; target ID is the caller-supplied, authorized resource. No names, mailbox, body, moderation reason, policy text, row version or grant is exposed.

Within one repeatable-read transaction, existing room/permission/participant/moderator gates are reused before resolving targets. Creator moderation requires current global stewardship; other moderators require current accepted participation and consent. Own account/session/eligible role lifetimes come from the shared `readCommandAuthority` snapshot, also used by the existing base endpoint. Existing command/read behavior and locking are unchanged; additional row-version locks are confined to this metadata method.

The target epoch binds room row version, actor's current membership and preference row versions, current account/session/permission epoch, target type/ID/row version, peer account row version, peer current preference/history row versions and both directions of retained contact-block rows/versions. Retained-ID demotion/reappointment, actor/peer consent and peer/block changes cannot silently preserve the same lifetime metadata. Snapshot conflicts, malformed/unbounded versions and unknown role/target shapes fail closed. This is not a deployed physical-restore/XID-wrap/key-rotation policy.

Member targets must belong to the room and be pending, accepted or banned. The current native operator set is returned: remove/ban for eligible targets, creator-only promote/demote with current global stewardship and the target's active account/current accepted consent, or unban for banned targets. This also reflects the native membership database guard, not merely the existing form's status label. Actor/creator and unavailable targets are refused. The endpoint does not add a new right to appoint/remove moderators or bypass current command revisions.

Message targets must belong to the room, fall within the actor's precise accepted-at history boundary and pass existing bilateral block visibility. Current hide/restore and moderation revision are returned without fetching encrypted message bodies or moderation reasons. Moderation event revisions are not target-lifetime epochs: hide/restore can change the current operation/revision while the immutable message and authority lifetime remain the same. A future adapter must separately bind operation and recheck current revision/eligibility; it cannot reuse a historical revision or treat a matching epoch as authorization to submit.

Historical messages from a disabled author remain eligible for the same moderation gates as existing native history; peer account version changes still invalidate lifetime metadata. This is not invitation eligibility. Invitation and safety-report/review context types remain unsupported rather than inheriting member/message privileges.

Reads issue no domain mutation, message acknowledgement, audit/notification/receipt insertion or external-provider call. Room advisory/row locks serialize the snapshot but persist no new records. Existing command endpoints remain the final fresh authority, consent, operation and revision gates.
