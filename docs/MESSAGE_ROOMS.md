## Retained Records

- Separate room preferences default off and use increasing revisions with immutable matching preference history.
- Rooms retain title, purpose, policy reference, retention rule and creator as immutable definitions. They start draft; activation requires a different reviewer and activation time. Closing is permanent, including closing an unpublished draft without invented approval evidence.
- Memberships retain invitation origin and revisioned pending/accepted/declined/left/removed/banned state. Acceptance binds the accepting account, timestamp and current enabled room-consent revision. Pending invitations cannot contain acceptance evidence.
- A single live pending/accepted/banned membership per account/room prevents duplicate invitations and bypassing an active ban. Unban ends the ban as left, not accepted; another invitation/acceptance is needed. Past membership windows remain retained and acceptance/end facts cannot be rewritten.
- Re-enabling preferences does not restore old membership authority: posting/moderation require the current preference revision to equal the retained acceptance revision. New explicit acceptance requires a new membership record after ending the old one.
- Message bodies use bounded opaque envelope columns, immutable account/membership identity, exact bigint positions and text/action/notice kinds. Notices require an accepted moderator or the accepted room creator. Historical ciphertext/envelope validity and identity-bound encryption still require application commands; this schema alone does not prove encryption.
- Append-only hide/restore moderation has sequential revisions, actor and opaque reason evidence. Current accepted moderator/creator membership and current consent are required. Room membership history and actor-bound receipt storage are retained; history rows must match the current membership revision/state/role.

These database guards do not replace authenticated application permission checks. `server/modules/message-rooms.js` now enforces self-only acceptance and authorized moderator grants, records membership history, and commits business state, metadata-only audit and keyed receipts atomically. Direct privileged database writes remain outside native session authority; schema-only writes are not proof of institutional appointments or approvals.

## Serialization

Room lifecycle, membership changes, postings and moderation share a room transaction advisory lock. Posting and moderation additionally hold shared locks on current preference/account records, so concurrent consent/account changes wait for an in-flight write. Native commands lock rooms before account/preference rows; preference changes serialize by actor without taking room locks after preference/account locks.

Closed rooms refuse posting, moderation and membership changes. Retained history is not erased. Native reads require current accepted membership, enabled matching consent and fresh active account/self authority; former members and pending invitations cannot read. Readers see only messages from their current acceptance onward, compared at PostgreSQL microsecond precision. Re-invitation does not restore previous history. Closing retains reads for still-consenting accepted members. No public/private-history access follows automatically from a room's existence or a staff role.

## Native Authority / Commands

- `rooms.self` is provisioned to explicit existing human roles, not arbitrary custom roles, auditors, service identities or sharing-only recipients. Every request rechecks active account/current effective assignments. Private consent remains independent.
- Global `rooms.manage` grants room drafting and explicit creator joining. Only a currently accepted creator with current global stewardship can appoint/revoke moderators. Creator moderation requires fresh stewardship; self-appointment cannot preserve it after role loss.
- Global `rooms.approve` grants independent activation and permanent closure, not message/member-list access. Different creator/reviewer accounts are mandatory for activation. New `room_steward` and `room_approver` roles have no working appointments.
- Invitation targets are exact known eligible opted-in mailboxes with coarse unavailable errors, never an account search directory. Pending invitees explicitly accept/decline; accepted members can leave even after consent becomes stale. Accepted moderators/eligible creator can invite, remove, ban and unban. Only the creator can remove another moderator; bans retain evidence and unban requires new invitation/acceptance.
- Text/action/notice bodies and membership/moderation reasons are encrypted with identity-bound envelopes. Notices require current moderator authority. Hide/restore has revision guards and encrypted reasons; hidden bodies are never decrypted into participant responses, even for moderators. No private-history investigation endpoint is introduced.
- Current private contact blocks conservatively exclude both peers' room message rows and deny direct invitations/moderation across the block. Blocking does not erase messages, end room membership or hide a moderator's authorized membership roster. Broader institutional block/roster policy remains an explicit review requirement.
- Room/member lists use 25-row pages; messages use 30-row exact bigint cursors. Invitations are limited to 50/day and messages to 30/minute per actor. Actor serialization covers counts and receipts; room locks protect posting/lifecycle/moderation. Read audits contain metadata only, not bodies, mailboxes or reasons.
- Every command has an actor-bound keyed receipt and canonical input digest. Changed reuse fails; committed replay adds no records. Send/moderation/invitation replays recheck current participation/moderator gates before returning a receipt. UI pending commands retain the original request/body in memory until success or explicit discard; session/route changes clear private state, and denied room responses clear rendered room history.

HTTP namespace: `/api/message-rooms`. Root GET/POST reads metadata/creates a draft; GET `/changes` returns a participant-scoped keyed change token; PUT `/preferences` records separate consent; POST `/:room/activate`, `/close`, `/join` handles lifecycle/creator participation. GET/POST `/:room/members` lists/invites; POST `/:room/members/:membership/:operation` handles acceptance/decline/leave/removal/ban/unban/promotion/demotion. GET/POST `/:room/messages` reads/posts; POST `/:room/messages/:message/moderate` hides/restores. Unsupported/repeated filters and authority/content injection fields are refused; responses are no-store.
