# Personal Notification Inbox

Guide Stage1 reusable notifications and the cross-cutting student portal now have an authenticated personal inbox at `#messages`. The existing header bell links there on desktop and mobile. Applicants/students and staff use their existing portal/registry sessions; where both are present the account selector is explicit. This is a portal view of retained non-secret notices, not a new email/SMS sender or evidence of external delivery.

## Ownership And Privacy

`GET /api/notifications/me` requires an active authenticated session, not staff `notification.send` authority. Every database query uses that session's account ID. Recipient filters are not accepted. Each item projects only `id`, `subject`, `body`, `createdAt` and `readAt`. Payload variables, explicit email addresses, recipient/template IDs and transport status are not returned. Text is escaped and rendered as plain text, never HTML or automatic links.

Sensitive payloads are excluded, including malformed sensitivity flags. Legacy non-sensitive payloads without the flag remain visible only when subject/body are strings. Password-recovery, account-activation and staff-invitation template codes are excluded even if a legacy sender omitted sensitivity metadata. Null-recipient notifications cannot be claimed by email or adopted by another account. Unknown/missing/other-account/hidden IDs all return the same404 for read acknowledgement. Staff-wide queue APIs retain their existing separate permission boundary; inbox access does not grant send/preview/admin queue authority.

## Paging And Reading

`view=all|unread|read`, `limit=1..50` (default20) and an opaque `cursor` are the only filters. Unsupported, repeated, malformed or oversized fields fail400. Impossible calendar dates, year zero and normalized24-hour timestamps are rejected before SQL; legitimate leap days remain valid. A repeatable-read snapshot keeps page rows and total/unread counts consistent. Ordering is creation time then ID descending; the keyset retains the PostgreSQL timestamp's six fractional digits, rather than JavaScript's millisecond truncation. Counts cover all visible notices for this account; the selected view affects page membership. Live arrivals/read actions can change later pages; this is not a historical census. Successful paging/filter refresh returns to the inbox header instead of retaining the previous page's scroll position.

`POST /api/notifications/me/{id}/read` accepts only an empty JSON object. It locks an owned visible notice, writes its first `read_at` and the `notification.read` audit in one transaction. Concurrent/repeated calls return the same retained acknowledgement and create one audit. Audit failure rolls back the acknowledgement. It never modifies notification delivery `status`, dispatches externally or marks other notices read. Viewing the list does not automatically acknowledge anything. `read_at` means the recipient explicitly marked a portal copy as read, not an email opened/delivered receipt.

Additive migration078 adds only `read_at` and the recipient/time/ID paging index. Existing rows begin unread; no queued payload/status is rewritten. No reseed, broad reference reload, operational fixture or provider change is required. Retention/archival policy and institutional wording remain owner decisions, not a delete feature invented here.
