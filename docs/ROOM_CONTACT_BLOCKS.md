# Room Invitation Contact-Block Ordering

## Intended Boundary

New room invitations must observe bilateral private-contact blocks at the same canonical account-pair transaction boundary used by native private block/unblock commands. The invitation must resolve a mailbox to an account ID, lock that pair, then recheck the exact resolved account/mailbox, current recipient account/grants/consent and both directions of active blocks before insertion/history/audit/receipt. Actor/room/moderator/permission/capacity gates remain independent. A mailbox reassignment between initial resolution and eligibility must not silently invite a different account whose pair was never locked.

First insertion of a block is as important as reactivating a retained inactive block: locking only existing block rows cannot protect absence. A native block transaction that owns the pair first must finish before the invitation rechecks eligibility. A valid invitation owning the pair first may commit its pending record before a subsequent block; the block must then prevent fresh invitations. Successful identical authorized receipt replay remains a retained result, not new participation, a restored private conversation or cancellation/retraction of a prior response. Changed input must still conflict, and pending room membership requires explicit recipient action.

Existing block filtering of room bodies/moderation remains separately tested by `message-rooms.spec.js`. This stage does not silently cancel retained invitations, ban/evict existing room members or change explicit acceptance semantics. Block ordering is specified for the native commands using the pair lock, not arbitrary direct database writes. Institutional retention/investigation/key/import/provider policy remains external; account names without presence and no automatic word filter remain unchanged.
