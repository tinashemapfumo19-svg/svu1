# Native Composer History

Implemented and verified 2026-10-12. All 613 unit tests, 24 desktop/mobile browser cases and 22 smoke scripts pass on the unchanged guarded source. This stage covers private/room message composition, not a generic replay protocol for every structured administrative command.

## Source Boundary

Read the supplied public `pfcclient.js` `doSendMessage`, `historyUp` and `historyDown` implementations without executing them. The legacy client appends raw attempted input before transport/command classification/truncation, shares an unbounded client list, caches a partially written input while navigating and intercepts textarea arrow keys. Native typed administrative actions remain explicit permission/revision-guarded controls; slash-prefixed message text is preserved as literal text, not executed or silently classified as a legacy operator command.

## Native Contract

- Each valid private conversation or accepted room participation owns an independent in-memory composer-history object. At most 25 submitted entries are retained, with at most 4000 characters per body (100000 total body characters), plus one bounded live-draft snapshot while browsing. Rows contain exact original submitted body, message kind and bounded request key. No body or key is put in a history button/counter attribute, local/session storage, a cookie or an API read response.
- Capture occurs on an actual native submission attempt, not only after success, and does not copy other authors' server history, report reasons, invitation emails or structured moderation/definition/review forms. Failed/uncertain sends remain recallable after their unresolved retry state is resolved. Body whitespace and literal markup/slash text are not normalized or truncated by this client buffer; existing server validation/outer-whitespace trimming remains unchanged.
- A frozen request retry does not add another history entry. Recall never restores the old request key: deliberately submitting a recalled candidate creates a new request/intent. Room send kinds are retained and restored; unavailable kinds refuse navigation before changing position or the draft, and current role/consent changes discard the owning context.
- Previous/next controls have explicit accessible names/tooltips and are non-submit buttons. They stop at the oldest entry and return to the original unfinished body, kind and caret selection after the newest. Editing a recalled candidate does not rewrite a historical entry or the saved unfinished draft. A new submission ends that browsing session as an explicit new intent.
- Clear composer history removes retained body/key rows and the saved navigation draft, leaves the current actual field/kind/selection unchanged and focuses the composer. It does not erase server messages, acknowledge reads, change consent, reset a server receipt or issue an API command. This is distinct from Clear conversation/room display.
- Textarea Up/Down, multiline editing and Tab navigation retain their native behavior. No input keyboard shortcut, nickname completion, online directory, room alias or automatic word-filter path is added.
- Busy/frozen/disabled/disconnected controls cannot navigate or clear. Private history is also disabled while a private send key is unresolved; an existing deliberate manual draft edit can clear that key and re-enable navigation as before. Global frozen room-pending commands preserve the existing complete field/command lock.
- Refresh, ordinary redraw and tab switching retain a valid participant's history independently of message paging/display/formatting. Closing/discarding a context, block/close/revision or preference change, leave/rejoin, role/membership replacement, identity departure, authority refusal or reload cannot revive an old history. These are client lifecycle protections, not a claim of cryptographic memory erasure against browser extensions or a debugger.
